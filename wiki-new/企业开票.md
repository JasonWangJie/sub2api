# 企业开票

[返回文档索引](文档索引.md)

本文记录 `v0.1.178.14` 已实现的企业开票流程，包括用户申请、管理员处理、历史开票补录，以及申请被拒绝后的重新申请规则。

## 功能开关与页面

企业开票由设置项 `enterprise_invoice_enabled` 控制，迁移后的默认值为 `false`。

| 角色 | 页面 | 开关关闭时 |
|---|---|---|
| 用户 | `/invoices` | 导航隐藏，路由不可用 |
| 管理员 | `/admin/invoices` | 导航隐藏，路由不可用 |

后端的开票服务同样检查该开关，不能仅依赖前端隐藏。管理员完成配置和迁移验证后，再在后台设置中启用。

## 用户申请流程

用户可以选择以下已完成且金额大于零的余额充值记录：

- 余额支付订单；
- 符合条件的余额兑换码记录。

管理员赠送余额和推广返利转入不属于可开票充值，列表会显示其不可选原因。支付订单自动关联的兑换码不会重复计入。

一次申请所选记录的合计金额不得低于 `1000.00`。提交时保存企业邮箱、税号、企业名称及充值明细的不可变快照；后续修改常用企业资料不会改写历史申请。

申请状态与充值来源占用规则如下。`HISTORICAL_COMPLETED` 是充值记录的历史开票状态，不是申请状态：

| 状态或标记 | 含义 | 来源能否再次选择 |
|---|---|---|
| `PENDING` | 等待管理员处理 | 否 |
| `COMPLETED` | 已完成开票 | 否 |
| `REJECTED` | 管理员已拒绝 | 是 |
| `HISTORICAL_COMPLETED` | 上线前已线下开票，由管理员补录 | 否 |

被拒绝后，原申请及其企业信息、充值明细、拒绝时间和拒绝理由仍保留在“申请记录”中。用户端会直接显示拒绝理由；用户修正资料后，可以重新选择原充值记录并创建一条新申请，系统不会修改或覆盖旧申请。

## 管理员处理

管理员可以按状态筛选申请，并按申请号、开票邮箱、税号或企业名称搜索。只有 `PENDING` 申请可以执行以下操作：

- 完成：将申请更新为 `COMPLETED`；
- 拒绝：将申请更新为 `REJECTED`，拒绝理由必填，长度为 1 至 1000 个字符。

“历史开票补录”用于登记功能上线前已经线下开票的充值记录。历史标记不可撤销，并显示为 `HISTORICAL_COMPLETED`。

历史补录列表对来源的显示规则：

| 来源当前状态 | 历史补录列表状态 |
|---|---|
| 未申请 | 可补录 |
| 申请为 `REJECTED` | 可补录 |
| 申请为 `PENDING` 或 `COMPLETED` | 已申请 |
| 已有历史标记 | 历史已开票 |

因此，被拒绝的订单不能继续显示为“已申请”；它既可由用户重新申请，也可由管理员按实际线下开票情况补录。

## 接口

用户接口：

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/v1/payment/invoices/profile` | 获取最近一次企业资料 |
| `GET` | `/api/v1/payment/invoices/records` | 获取充值记录及可选状态 |
| `GET` | `/api/v1/payment/invoices/applications` | 获取申请记录和拒绝理由 |
| `POST` | `/api/v1/payment/invoices/applications` | 创建申请 |

管理员接口：

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/v1/admin/payment/invoices` | 筛选、搜索申请 |
| `GET` | `/api/v1/admin/payment/invoices/records` | 查询历史补录候选记录 |
| `POST` | `/api/v1/admin/payment/invoices/historical-marks` | 创建不可撤销的历史开票标记 |
| `GET` | `/api/v1/admin/payment/invoices/:id` | 获取申请详情 |
| `POST` | `/api/v1/admin/payment/invoices/:id/complete` | 完成待处理申请 |
| `POST` | `/api/v1/admin/payment/invoices/:id/reject` | 拒绝待处理申请 |

所有写接口都必须携带 `Idempotency-Key`。同一调用发生网络重试时应复用原键；不能把同一键用于不同请求体。

## 数据一致性

- 创建申请和历史补录都会按 `source_type + source_id` 获取 PostgreSQL advisory transaction lock，防止并发重复占用同一充值来源。
- 活跃占用只包括 `PENDING` 和 `COMPLETED`；`REJECTED` 不再占用来源，但其申请明细快照不会删除。
- `invoice_historical_marks` 继续保留 `(source_type, source_id)` 唯一约束，历史标记不可重复或撤销。
- 管理端历史补录和用户端可选记录使用同一套占用判定，避免两端状态不一致。

## 迁移与升级

企业开票依赖以下迁移，必须按编号顺序执行：

| 迁移 | 作用 |
|---|---|
| `228_ZJ_invoice_applications.sql` | 企业资料、申请和申请明细 |
| `229_ZJ_historical_invoice_marks.sql` | 不可变历史开票标记 |
| `230_ZJ_enterprise_invoice_setting.sql` | 默认关闭的功能开关 |
| `231_ZJ_allow_rejected_invoice_reapplications.sql` | 允许被拒绝来源重新申请 |

迁移 `231` 删除申请明细来源的全局唯一约束，并重建普通查询索引 `invoiceapplicationitem_source_type_source_id`。是否允许占用由事务锁和申请状态共同决定，而不是由全局唯一索引决定。

升级后再回滚到不认识“拒绝后复用”规则的旧版本可能与重复的申请明细冲突。需要回滚时，应先停写并核对是否已有同一来源对应多条申请历史。
